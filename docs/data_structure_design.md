
# Data Structure Design Summary

## Purpose

This data structure converts the raw DataFest CSV files into a layered dataset for **patient timeline tokenization** and **patient journey analysis**.

The design is centered on `encounters.csv`, because each encounter is the core event in a patient’s observed timeline. Other CSVs add patient demographics, diagnosis details, department metadata, provider metadata, social determinant of health responses, and geography.

Our main goal is to represent each patient’s **full observed encounter history** as an ordered sequence of interpretable tokens.

In plain terms:


For each patient, what happened, when did it happen, where did care occur,
what primary diagnosis was recorded, what type of care was provided,
what were the time gaps, and what SDOH context was observed?

This supports:

* full patient-history tokenization
* encounter-level analysis
* patient-level sequence modeling
* transition/pathway analysis
* diagnosis-centered journey analysis
* social determinant of health analysis
* patient-level and diagnosis-level summaries
* clustering or modeling of patient timeline patterns

The overall pipeline is:

```text
Raw CSVs
→ cleaned dimension and fact tables
→ encounter-level analytic table
→ SDOH encounter summary
→ encounter table with SDOH attached
→ patient timeline event table
→ patient token sequence table
→ patient transition table
→ patient summary and model feature matrix
```

Diagnosis-specific journey tables are still useful, but they are supporting tables. The core tokenization object is now the **full observed patient timeline**, not only the diagnosis-specific journey.

# 2. Final table design

The final structure has three levels:

```text
Level 1: Cleaned dimensions and facts
Level 2: Encounter and SDOH analytic tables
Level 3: Patient timeline, sequence, transition, journey, and modeling tables
```

Suggested fields:

```text

```

Purpose:


Important rule:




Purpose:


Plain-language meaning:

```text
For each encounter, this table contains:

encounter timing,
encounter type,
primary diagnosis,
department information,
provider-role information,
geography information,
and all SDOH information recorded for that patient during that encounter.
```

# 5. Level 3: Patient timeline, sequence, transition, journey, and modeling tables

The main tokenization goal is to represent the **entire observed history of one patient**.

Therefore, the main Level 3 tables are patient-level timeline tables:

```text
patient_timeline_event
patient_timeline_sequence
patient_timeline_transition
patient_timeline_summary
model_feature_matrix_patient
```

Diagnosis-centered journey tables are still useful, but they are secondary/supporting tables.

```text

identify common care pathways
find fragmented care histories
find ED-heavy or hospital-heavy patient histories
find long-gap patient histories
compare sequence archetypes by SDOH domains
```

Possible supervised targets:

```text
future ED visit after index event
future hospital admission
long gap after hospital discharge
high utilization group
transition from outpatient to inpatient
no follow-up within 30 or 90 days
```

Important rule:

```text
Targets should be defined only after checking whether the relevant event types and date fields are sufficiently populated.
```

# 10. Design principles

## 10.1 Preserve raw keys

Do not rename or reinterpret keys without keeping the original fields.

Critical keys:

```text
EncounterKey
PatientDurableKey
DurableKey
DiagnosisKey
PrimaryDiagnosisKey
DepartmentKey
ProviderDurableKey
AttendingProviderDurableKey
DischargeProviderDurableKey
CensusBlockGroupFipsCode
GEOID
```

---

## 10.2 Keep provider roles separate

Do not collapse these fields into a single provider field:

```text
ProviderDurableKey
AttendingProviderDurableKey
DischargeProviderDurableKey
```

They represent different roles in the encounter.

---

## 10.3 Use `DiagnosisValue` for diagnosis-centered journeys

Use:

```text
PatientDurableKey + DiagnosisValue
```

for diagnosis-specific journeys or diagnosis episodes.

Do not use:

```text
PatientDurableKey + PrimaryDiagnosisKey
```

as the final diagnosis journey definition unless doing a key-level sensitivity check.

---

## 10.4 Use `PatientDurableKey` for full-history tokenization

For the main tokenization goal, use:

```text
PatientDurableKey
```

as the sequence grouping key.

The main patient timeline is:

```text
all observed encounters for one PatientDurableKey,
ordered by Date, AdmissionInstant, and EncounterKey
```

---

## 10.5 Keep SDOH responses long before summarizing

The source SDOH table has one row per answered question.

Keep this table:

```text
fact_sdoh_response
```

Then create:

```text
sdoh_encounter_summary
```

This avoids duplicating encounter rows.

---

## 10.6 Do not assume SDOH answer scoring

For SDOH:

```text
Domain
DisplayName
AnswerText
```

should be preserved.

Do not create risk labels until actual answer values have been reviewed.

---

## 10.7 Treat missingness as informative

Different missing-like values may mean different things.

Suggested normalized missingness classes:

```text
asked_not_answered_or_unable
not_recorded_or_unknown
system_missing
structural_not_applicable
known_value
```

Keep both:

```text
original value
normalized missingness class
```

where possible.

---

## 10.8 Maintain multiple grains

The design intentionally keeps several units of observation:

```text
patient
encounter
SDOH response
patient timeline event
patient timeline transition
patient token sequence
patient-diagnosis journey
diagnosis episode
diagnosis group
modeling row
```

This prevents forcing all analysis into one overly wide table.

# 15. Final analytic concept

The main analytic object is now:

```text
an observed patient timeline
```

Defined as:

```text
all observed encounters for one PatientDurableKey,
ordered by Date, AdmissionInstant, and EncounterKey
```

The main sequence object is:

```text
one tokenized event per encounter within a patient’s full observed timeline
```

The main transition object is:

```text
one transition between each pair of consecutive encounter events in a patient’s full observed timeline
```

The supporting diagnosis-centered object is:

```text
an observed patient-diagnosis journey
```

Defined as:

```text
all observed encounters for one PatientDurableKey and one DiagnosisValue,
ordered by Date, AdmissionInstant, and EncounterKey
```

Together, the final structure supports:

```text
What happened to each patient over time?
When did encounters happen?
How long were the gaps?
Where did care occur?
What primary diagnoses appeared?
What care settings were involved?
Did the patient move from outpatient to ED or hospital care?
Were SDOH responses observed?
Do patients with different SDOH or demographic profiles have different timeline patterns?
Which patient histories look fragmented, delayed, ED-heavy, hospital-heavy, or high-complexity?
Which diagnosis groups appear in certain patient timeline archetypes?
```

# 16. Short summary

Three-level data structure design. For full details, see `docs/data_structure_design.md`.

## Level 1: Cleaned / standardized base tables

Cleaned dimensions and facts:

```text
dim_patient
dim_diagnosis
dim_department
dim_provider
dim_geography
fact_encounter_base
fact_sdoh_response
```

These preserve the raw table grains while standardizing missingness, types, and key fields.

## Level 2: Encounter and SDOH analytic tables

```text
encounter_enriched
```

One row per encounter. Combines encounter information with patient, diagnosis, department, provider-role, and geography metadata.

```text
sdoh_encounter_summary
```

One row per `EncounterKey + PatientDurableKey`. Summarizes all SDOH information recorded for that patient during that encounter.

```text
encounter_enriched_with_sdoh
```

One row per encounter. This is `encounter_enriched` plus the attached SDOH summary. It is the main source table for tokenization.

## Level 3: Patient timeline, sequence, transition, and supporting journey tables

Main patient-tokenization tables:

```text
patient_timeline_event
```

One row per encounter event in a patient’s full observed timeline.

```text
patient_timeline_sequence
```

One row per patient, containing that patient’s ordered token sequence.

```text
patient_timeline_transition
```

One row per transition between consecutive encounters in a patient’s full timeline.

```text
patient_timeline_summary
```

One row per patient, summarizing the full observed timeline.

```text
model_feature_matrix_patient
```

One row per patient, containing patient-level sequence, transition, SDOH, diagnosis, geography, and utilization features for clustering or modeling.

Supporting diagnosis-centered tables:

```text
diagnosis_episode
journey_episode
journey_event_sequence
journey_transition
diagnosis_group_summary
```

These preserve the original diagnosis-journey framing and help analyze specific primary-diagnosis pathways.
